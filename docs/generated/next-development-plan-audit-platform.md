# RepoGraph 审计流程能力对齐与下一步开发计划

> 对齐基准：靶标资产接入、多语言静态检测、数据流与权限分析、智能降噪、动态验证、
> 标准化交付、规则迭代及底层通用支撑。
>
> 评估日期：2026-07-26。结论基于 `CONTEXT.md`、现有源码、测试和
> `docs/generated/roadmap-codesec-triage-agent.md`，不是仅按规划文档推断。

## 结论

RepoGraph 已经具备“多语言源码索引 → 外部 SAST 报警导入 → 调用图/污点/Context Pack
证据融合 → 启发式研判 → Markdown/JSON 输出 → 人工反馈”的基础主链路，但还不是完整的
端到端代码审计平台。

下一阶段不应重写 CodeQL、Semgrep、Slither 等成熟扫描内核，而应继续保持“代码智能与报警研判层”
定位，优先补齐四个闭环断点：

1. **输入闭环**：安全接入源码归档包，形成可复用的资产画像和扫描计划。
2. **检测闭环**：统一编排外部扫描器，并把结果归一化到 `ExternalFinding`。
3. **研判闭环**：补足路由鉴权语义、历史反馈复用和 source/sink 路径一致性证据。
4. **交付闭环**：形成审核队列、标准化多格式报告和可量化的规则效果评估。

动态验证和 OOB 核验属于新的高风险执行边界，应在上述静态闭环稳定后，以隔离运行时和严格安全策略
单独建设，不能直接复用当前索引服务进程执行不可信项目。

## 能力对齐矩阵

- **已实现**：存在可调用入口、核心实现和对应测试或活体验证。

- **未实现**：仓库中没有对应领域能力；仅有通用基础设施不视为实现。

## 架构边界

后续实现继续遵守以下边界：

1. `repograph-core` 只定义领域模型和接口，不引入第三方依赖；归档、容器、扫描器和报告实现放在
   `repograph-app` 或新的基础设施子模块。
2. 外部扫描器通过适配器产出 `ExternalFinding`，不把 CodeQL、Semgrep、Slither 的专有模型渗透到
   `VulnFinding`、`ContextPack` 或图存储。
3. `ExternalFinding` 表示外部工具事实，`VulnFinding` 表示 RepoGraph 内部发现，研判结论继续独立保存，
   不混用状态机。
4. 动态验证必须运行在独立受限进程或容器；RepoGraph 主服务只下发任务并接收结构化证据。
5. LLM 只能解释完整的 citation-ready 证据包，输出必须标记为辅助意见，不能直接把发现变为
   `CONFIRMED` 或覆盖人工反馈。
6. Slither 可先作为独立扫描器导入结果；在增加 Solidity `CodeUnit` 解析前，不宣称已支持
   Solidity 上下文定位、调用图或污点融合。

## 任务拆分

### T1 安全归档接入并完成一次目录索引

- **优先级**：P0
- **类型**：AFK
- **状态**：核心验收完成（2026-07-26）；主动取消统一归入 T10
- **状态**：已完成（2026-07-26）
- **被阻塞于**：无
- **要构建什么**：用户上传 ZIP/TAR 源码包后，系统在隔离工作目录中安全解压，拒绝路径穿越、
  符号链接逃逸、超限文件和压缩炸弹，然后复用 `IndexPipeline` 完成项目索引。
- **验收标准**：
  - [x] 支持至少 ZIP 和 TAR.GZ，两种格式使用同一接入结果模型。
  - [x] 限制归档总大小、解压后大小、文件数、单文件大小和目录深度。
  - [x] `../`、绝对路径、符号链接逃逸和重复覆盖条目均被拒绝并产生结构化错误。
  - [x] 成功接入返回 `projectId`、工作目录、文件统计和异步索引任务标识。
  - [x] 临时目录在失败和项目删除后可清理，不删除用户原始文件。
- **验证方式**：使用正常包、混合语言包、Zip Slip、符号链接、压缩炸弹和超限 fixture 做集成测试。

### T2 生成资产画像并给出高风险扫描计划

- **优先级**：P0
- **类型**：AFK
- **状态**：已完成（2026-07-26）
- **被阻塞于**：T1
- **要构建什么**：接入项目后输出 `ProjectAssetProfile`，展示语言占比、框架、业务/测试/生成文件、
  入口点、依赖清单和高风险特征，并生成应运行哪些扫描器及为何运行的扫描计划。
- **验收标准**：
  - [x] 业务、测试、文档、生成代码和未知文件具有明确分类及分类依据。
  - [x] 资产画像能识别当前已支持的 Spring、JAX-RS、MyBatis 和构建系统。
  - [x] 高风险特征至少覆盖公开 HTTP 入口、危险 Sink、敏感配置、依赖 CVE 和高变更热点。
  - [x] 扫描计划只选择与语言/构建上下文匹配的扫描器，且允许人工覆盖。
  - [x] 分类不确定时保留 `UNKNOWN` 和原因，不静默归入业务代码。
- **验证方式**：对 Java Web、Python、C 和混合仓库 fixture 做资产画像快照测试。

### T3 编排一次外部扫描并归一化报警

- **优先级**：P0
- **类型**：AFK
- **被阻塞于**：T1
- **要构建什么**：定义通用 `ScannerAdapter` 边界，先打通 Semgrep 和 CodeQL CLI 的
  “启动 → 超时 → 采集结果 → 导入 `ExternalFinding` → 记录扫描元数据”最短路径。主动取消与异步
  任务状态机一起归入 T10，避免同步和批量阶段形成两套模型。
- **验收标准**：
  - [x] 适配器声明支持语言、所需命令、版本、输出格式和运行前置条件。
  - [x] 命令参数以参数数组构建，不经 shell 拼接；工作目录和输出目录均受控。
  - [x] 单个扫描器失败不影响其他扫描器，错误、退出码、耗时和工具版本可查询。
  - [x] Semgrep 与 CodeQL 结果复用现有导入器，重复导入按指纹幂等关联。
  - [x] 未安装工具时返回 `UNAVAILABLE`，不把环境问题伪装成“零漏洞”。
- **验证方式**：伪 Semgrep/CodeQL CLI 集成测试均已覆盖；本机 Semgrep 1.171.0 真实冒烟成功。
  当前环境未安装 CodeQL，其真实冒烟待工具可用后执行，缺失状态已覆盖 `UNAVAILABLE`。

### T4 生成路由—鉴权—资源访问证据

- **优先级**：P0
- **类型**：AFK
- **被阻塞于**：无
- **要构建什么**：以 Java/Spring 为第一片，从入口点和注解提取 HTTP 方法、路径、控制器级与方法级
  鉴权约束，沿调用图关联资源访问和危险 Sink，形成可引用的 `AuthorizationEvidence`。
- **验收标准**：
  - [x] 支持 Spring Security 常见方法级注解，并正确合并类级和方法级约束。
  - [x] 区分“未发现鉴权证据”和“已确认无鉴权”，不做过度结论。
  - [x] 证据包含 route、principal/role 表达式、目标资源、调用路径和源码 citation。
  - [x] 鉴权注解只作为约束候选；动态配置、过滤器和网关策略缺失时列入 `missingInfo`。
  - [x] 不新增含义不明的 `metadata` key；如需新增，先更新 `CONTEXT.md` 标准 key 表。
- **验证方式**：类级/方法级鉴权、覆盖关系、无本地证据、过滤器策略候选、间接资源访问和
  资产级 REST fixture 已覆盖。

### T5 让历史反馈、路径一致性和漏洞变体参与研判

- **优先级**：P0
- **类型**：AFK
- **被阻塞于**：T4
- **要构建什么**：把精确指纹反馈、项目级规则反馈和 source/sink/保护点的路径一致性证据输入
  `TriageReportService`；同时从已确认发现的规则、CWE、Sink、数据流特征和相似代码出发召回候选变体，
  形成可解释的降噪与变体研判路径。
- **验收标准**：
  - [x] 同指纹历史 `FALSE_POSITIVE` 作为强提示，但代码或规则版本变化后不会无条件复用。
  - [x] 项目级规则抑制必须有作用域、理由、创建人、有效期和审计记录。
  - [x] 只有保护点覆盖报警 source 到 sink 的相关路径时，才能提高“已有有效防护”的置信度。
  - [x] 历史反馈和路径证据在报告中各自拥有来源说明，不覆盖外部工具原始事实。
  - [x] 漏洞变体候选包含与种子发现的相似依据和源码 citation，并按指纹去重。
  - [x] 变体候选创建时保持 `SUSPECTED` 或 `NEEDS_REVIEW`，不因相似性自动确认漏洞。
  - [x] 所有自动结论仍允许人工改写，并保存新反馈。
- **验证方式**：使用反馈命中/失效、规则抑制过期、保护点在路径内/外、多入口绕过及
  同类漏洞变体阳性/阴性测试；上述 fixture 均已覆盖。

### T6 增加受约束的 LLM 辅助复核

- **优先级**：P1
- **类型**：HITL
- **被阻塞于**：T5
- **人工决策点**：允许的模型提供方、数据是否可出域、脱敏策略、成本与超时上限。
- **要构建什么**：以可插拔接口接收 `ContextPack` 和启发式报告，输出结构化辅助意见、引用和不确定性；
  不直接改变漏洞状态。
- **验收标准**：
  - [x] 未配置模型时完整退化到现有启发式流程。
  - [x] 输出引用必须来自输入 citation；未知事实必须进入缺失信息而不是生成新证据。
  - [x] 响应明确标记 `advisoryOnly=true`，禁止自动写入 `CONFIRMED`。
  - [x] 有超时、重试、预算、脱敏和审计日志，日志不记录源码全文或密钥。
  - [x] 使用固定样本集比较启发式与 LLM 辅助后的准确性、耗时和成本。
- **验证方式**：契约测试、伪模型测试、提示注入样本和固定人工标注离线评估均已覆盖。
- **当前边界**：只实现提供方中立模型接口和关闭模型。真实外部模型适配器必须在部署方明确
  提供方、数据出域、脱敏和费用策略后单独接入，不能仅把 `enabled` 改为 true 即发送源码。

### T7 在隔离容器中复现一个可回显漏洞

- **优先级**：P1
- **类型**：HITL
- **被阻塞于**：T3、T5
- **人工决策点**：允许执行的项目来源、容器运行时、安全基线、网络和资源策略。
- **要构建什么**：先选一个 Java HTTP 命令注入或 SQL 注入 fixture，打通
  “构建目标 → 启动隔离运行时 → 健康检查 → 发送载荷 → 采集响应/日志 → 关联 `ExternalFinding`”
  的最小动态验证路径。
- **验收标准**：
  - [ ] 主服务不直接执行目标代码；容器默认无特权、只读根文件系统、限 CPU/内存/时间。
  - [ ] 默认禁止外网，仅开放验证控制面所需的最小网络。
  - [ ] 载荷来自版本化模板，禁止任意命令字符串透传。
  - [ ] 动态证据记录镜像、构建日志摘要、请求、响应摘要、时间和关联指纹。
  - [ ] 失败、超时和不可构建均返回 `INCONCLUSIVE`，不自动判定误报。
- **验证方式**：阳性 fixture、已修复 fixture、构建失败、启动超时、网络阻断和资源超限测试。

### T8 验证无回显和上传链路

- **优先级**：P2
- **类型**：HITL
- **被阻塞于**：T7
- **人工决策点**：OOB 域名/平台、出网政策、数据保留周期和授权审计要求。
- **要构建什么**：在动态验证证据模型上增加短期 OOB token、DNS/HTTP 回连关联，以及文件上传
  “请求 → 存储 → 解析/执行 → 回连或可观察副作用”证据链。
- **验收标准**：
  - [ ] OOB token 单任务唯一、短期有效、不可枚举，并与 finding 指纹关联。
  - [ ] 未收到回连只表示 `INCONCLUSIVE`，不能证明漏洞不存在。
  - [ ] 上传文件使用无害 canary，不提供持久化后门或破坏性载荷。
  - [ ] 证据包含请求、服务端处理位置、回连事件和时间相关性。
  - [ ] 所有 OOB/上传验证必须显式授权并留下审计记录。
- **验证方式**：DNS/HTTP 阳性、无回连、延迟回连、token 重放和上传链路中断测试。

### T10 批量扫描任务编排和 Slither 接入

- **优先级**：P2
